# NJEN — Supabase + Payload Responsibility Model

**Status: PLANNED — NOT IMPLEMENTED.** 22-09-2026. Neither Supabase nor Payload exists in the repository yet; no project, database, schema or account has been created. This document fixes *who owns what* before Week 2 setup, to avoid duplicated data, duplicated logic and later rebuilds.

Both are approved directions (register R6).

- **Supabase** = managed PostgreSQL, plus future member authentication and private file storage.
- **Payload** = the CMS and staff admin, running **inside** the NJEN Next.js app and storing its content in PostgreSQL.

---

## 2. Should they share PostgreSQL infrastructure?

**Recommendation: one NJEN-owned Supabase project (one PostgreSQL database) with two clearly separated data boundaries.** Not two databases.

- **Why share:**
  - One bill; the Pro plan's compute credit covers one instance.
  - One backup and **one restore test** covers everything.
  - One set of credentials and access to manage.
  - Future features can reference content (for example, an application referencing a job) without cross-database plumbing.
- **Why separate boundaries anyway:** content and application data have different owners, migration tools, access rules and security requirements.

| Boundary | Contents | Managed by | Migrations |
|---|---|---|---|
| Payload boundary | Payload collections, versions, staff users, sessions | Payload | **Payload's own migrations** — generated by Payload, committed to Git, run on deploy |
| Application boundary (`app` schema) | Everything in the Supabase rows of section 1 | NJEN application services | **Versioned SQL migrations** (Supabase CLI), committed to Git |

Rules:
1. Neither migration system alters the other's tables.
2. Application records refer to Payload documents by stable ID (for example `application.job_id`) with application-level integrity checks. Jobs are archived, never hard-deleted, so references stay valid.
3. The deploy runs Payload migrations and application migrations as separate, ordered steps.

## 3. ⚠ Architecture decision ARCH-1 — must be settled before Week 2 setup

**Risk (verified in Supabase's official documentation, 22-09-2026):**
- *"By default, your database has a `public` schema which is automatically exposed on data APIs."*
- *"A table in an exposed schema without RLS is readable and writable by any role with a grant on it."*

Payload's PostgreSQL adapter uses the `public` schema by default. If Payload is connected with default settings, **CMS tables could be reachable through Supabase's public Data API.** That includes staff users (with password hashes), unpublished drafts and moderation notes, which would be a direct breach of the public/protected boundary.

Nothing is implemented, so there is nothing to rebuild. The configuration choice must be made deliberately:

| Option | How | Pros | Cons |
|---|---|---|---|
| **A (recommended)** | Keep Payload in `public`. **Remove `public` from Supabase's exposed Data API schemas** (or disable the Data API while no browser-side Supabase access exists). Enable RLS with no policies on every Payload table as defence in depth. Put application tables in an unexposed `app` schema. If browser-side access is ever needed (post-launch), expose only a dedicated `api` schema with reviewed RLS policies. | Uses Payload's standard, supported configuration; closes the exposure at the source; no experimental features | Supabase Data API settings must be part of the environment checklist and re-verified at launch |
| B | Put Payload in its own `payload` schema with the adapter's `schemaName` option | Clean separation by schema | Payload documents `schemaName` as **experimental**; relying on it adds upgrade risk |
| C | Separate Supabase projects for Payload and the application | Strongest isolation | Extra cost and operations; two backups and restore tests; no in-database references |

Also required, whichever option is chosen:
- The Supabase **service-role key and database connection string stay server-only.** Never `NEXT_PUBLIC_`, never in client bundles.
- At launch no browser code talks to Supabase directly.

**Status:** ARCH-1 is a technical decision within the approved stack. **Option A is recommended.** It is recorded in `WEEK1_CLIENT_INPUT_REGISTER.md` so NJEN can object before Week 2. It is *not* being implemented today.

## 4. How pages and features read data

```
Browser ──► Next.js server (pages, route handlers)
               │
               ├─► Content services (e.g. lib/jobs.ts)
               │       └─► Payload Local API (server-side, no HTTP hop)
               │              └─► PostgreSQL — Payload boundary
               │       Returns explicit public DTOs (published, current records only)
               │
               └─► Application services (post-launch: accounts, performers, portal, billing)
                       └─► PostgreSQL — app schema (authorization check + RLS)
                       └─► Supabase Storage (private buckets, short-lived signed URLs)
```

- **Public pages** receive only DTOs from content services. `lib/jobs.ts` already implements this seam today, using sample data. Connecting Payload changes only that module.
- **Protected features** (post-launch) go through application services that verify identity, role, verification and ownership on the server, backed by RLS.
- **Payments** (post-launch) are confirmed by provider webhooks handled server-side. Prices are always read from configuration on the server, never from the browser.

## 5. Jobs: one owner

`DATABASE_AND_ROLE_MODEL.md` previously listed jobs as application tables (`jobs`, `job_sources`, `job_moderation`, `job_expirations`). The Master Business Rules (§4, §14) and the Implementation Plan (§11) make jobs **staff-managed CMS content** with moderation, expiry and archive. Keeping both would create two sources of truth.

**Resolved (documentation):** jobs are a **Payload collection**. Source, moderation state, expiry/closed state and featured flags are fields on that collection. The database model has been updated to match.

- **Post-launch employer submissions** from verified organizations are authorized by the application boundary, then created in Payload as **drafts** through the server-side Local API. They never publish automatically (Business Rules §4).
- **Post-launch applications and saved jobs** live in the app schema and reference the Payload job ID.

## 6. Identity: staff vs members

| Who | Where | When |
|---|---|---|
| NJEN staff (Admin, Editor/Moderator) | Payload users collection | Launch |
| Members, performers, industry users, organization members | Supabase Auth plus `app` profiles and role assignments | Post-launch |

The separation is deliberate: staff privilege stays separate from member and industry access (Business Rules §8, §14).

**Future decision (Phase A, not launch):** whether staff later sign in through the same identity provider. Payload provides extension points for custom authentication that would allow this. Either way, staff roles and member/industry roles remain separate capabilities.

## 7. Admin-configurable business values

Membership prices, the SAG-AFTRA discount (currently 40%), eligibility rules and the additional-photo price (currently $25) must be Admin-configurable (Addendum v1.1).

- **Recommended home:** a configuration table in the **app schema**, next to the billing and entitlement data that depend on it.
  - Edits restricted to Admin, with full audit history (who, what, when, previous value).
  - **Every transaction snapshots the price, discount and rule** applied at purchase, so later configuration changes never alter past records.
- **Admin editing screen:** decided in Phase A. Either a restricted custom view inside the Payload admin that calls the application service, or the CRM/admin area. The data itself stays in the app schema, keeping money-related values out of the editorial CMS.
- **Not acceptable:** prices in code, in environment variables, or supplied by the browser.
